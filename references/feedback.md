# 使用反馈与有边界的改进

闭环是：真实反馈 → 对应版本 → 本次修改 → 记录适用范围 → 必要时提议长期偏好 → 用户明确确认后应用。模型自评分和“文笔更高级了”的自述不算学习证据。

## 存放与读取

默认学习目录是当前项目 `output/social-posts/_learning/`，用户明确指定共享学习目录时使用该目录并在交付中注明。没有共享目录就不承诺跨项目记住；没有相关聊天的访问权限就不扫描其他聊天。

- `feedback.md`：按任务及稿件版本记录用户原话、定位、修改及结果。
- `preferences.md`：只保留明确确认的长期偏好及变更记录，注明 ID、平台、适用题型、来源、状态和撤回信息。

首次有实际反馈时再创建目录，不为了空白配置阻塞出稿。默认目录内创建 `.gitignore`，内容为 `*`，把私人反馈与偏好排除出普通 Git 添加；不要修改项目其他 Git 配置，也不声称这能移除已跟踪文件或历史泄漏。公开 Skill 包里只放方法，不放真实对话和用户反馈。不写 Codex 全局记忆，不在安装目录保存个人资料。

写作前只读取已确认偏好；用户要求总结经验时才汇总历史反馈。用户明确不保存时，文章、反馈和偏好全部只展示；不能写文件则说明未持久化，不声称下次一定记得。

## 每次反馈怎么处理

1. 定位当前稿件、平台与版本。记录最少必要信息，不复制整段私人对话。字段包括：任务 ID／稿件路径、用户原话、适用范围、动作、修改后版本、用户评价、长期状态。无需给每句话另建文件。
2. 本次明确修改要求立即作用于本次稿件。用户说“这个版本比较喜欢”记录为该版本偏好，不等于全面批准或授权发布。“内容可以，就一张图”只确认当前内容与配图选择。
3. 单次意见默认是局部反馈。同一篇的三轮修改仍只算一个任务，不算三次独立验证。可以提出一条可复用的候选经验，但候选不能默默成为默认规则。
4. 用户明确说“以后朋友圈都这样”“把它设为默认”等，且适用范围清楚时，直接更新对应已确认偏好，不再重复询问许可。单纯“记下这次意见”只授权留反馈，不授权把所有意见推广到以后。仅说“下次记住”而范围模糊时先保存，并简短确认是否作为长期偏好；不为此卡住已授权的本次修稿。
5. 相似反馈在不同任务重复出现时，可据来源提议确认一条长期偏好；没有明确确认前仍是候选。当前指令优先于长期偏好。新旧偏好冲突只更新相同平台和范围，保留撤回／替代记录，不删除历史以伪装一致。
6. 本轮结束只做一次“记录—建议”动作；不让生成器与评分器递归互相提高分数，也不自主修改 Skill 核心规则。用户明确要求维护 Skill 时，才按版本管理改源文件、验证后同步安装副本。个人偏好更新不需要改 Skill 版本，记录自身更新时间和变更即可。

交付时一句话说明“本次意见已记录为局部反馈／已确认的某范围偏好”，给路径；不要每次附一份学习报告或强制用户填写表格。

## 区分案例经验与长期规则

假设某篇历史分析稿经用户修改后采用问题切入、史料支撑，并选择一张时间轴，可把它记录为该篇的成功案例。候选经验是“历史材料较多时先聚焦问题，再用资料支撑”。不能推导成所有朋友圈都长写、必须总分总、不能有数字、每篇恰好一张图，也不能把用户偏好某一版等同于证明传播效果。这是假设的操作示例；真实反馈只进入项目私有学习目录。

今后修改风格规则，优先用原案例和一个不同题材做对照：能否解决原缺陷，是否损害另一题。通过只说明这两个例子符合要求，不宣称文风已经普遍提升。
